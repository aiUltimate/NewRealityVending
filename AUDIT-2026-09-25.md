# Repository Architecture Audit — 2026-09-25

## Executive finding
The repository has a strong strategic architecture, but it is currently a planning repository, not yet an executable MVP repository.

The highest-value next move is to convert the existing doctrine into a small, testable operating system:
Founder → Research → Rules → Product Twin → Compliance Decision → Simulated Pod → Transaction → Audit Event → Economics → Crowdfunding Evidence

The repository should remain the source of truth.

## 1. What is already strong
- Platform-first positioning rather than dependence on one cannabinoid.
- Clear PA regulated-retail architecture.
- Separation of technology, retail, and product businesses.
- Stage-gated roadmap.
- Fail-closed doctrine.
- SKU + jurisdiction + date compliance model.
- Human-review state and evidence hierarchy.
- Product digital twin, batch and COA traceability.
- Founder-as-first-moderator operating model.
- Unit economics and risk framework.
- Crowdfunding structure focused on measurable proof.

## 2. P0 — Execute before public crowdfunding

### P0.1 Executable repository
Current repository contains architecture but no runnable application.
Build: /app, configuration, database models, API, local development instructions, and tests.

### P0.2 Product database
Turn product.schema.json into actual records and validation.
Add data/products/products.json, sample non-regulated demo SKUs, evidence references, and validation tests.

### P0.3 Compliance rule database
Create data/compliance/rules.json, sources.json, and decisions.json.
Every rule needs: rule ID, jurisdiction, effective date, source, requirement, severity, status, reviewer, and last reviewed.

### P0.4 Simulation engine
Simulate: customer → catalog → compliance → payment → inventory → transaction → audit.
Deliberately test failure states.

### P0.5 Crowdfunding financial model
Replace planning percentages with conservative, base, and upside scenarios.
Calculate funding target, fees, prototype cost, burn, runway, machine cost, installation, inventory, pilot cost, contingency, and milestone unlocks.

## 3. P1 — Founder operating system
- Master backlog with ID, subsystem, task, priority, dependency, owner, status, evidence, and completion criterion.
- Research ledger: QUESTION → SOURCE → FINDING → CONFIDENCE → DECISION → NEXT ACTION.
- Decision log for major architectural choices and rejected alternatives.
- Evidence registry shared by legal, product, scientific, supplier, and operational claims.

## 4. P1 — Strengthen schemas
Product should eventually include source, concentration, amount, format, ingredients, claims, machine compatibility, economics, evidence IDs, batch IDs, and regulatory review.
Compliance decisions should include reason, restrictions, evidence snapshot, effective date, review date, human approval, and machine authorization.
Audit events should include jurisdiction, rule version, correlation ID, actor type, evidence IDs, and later an immutable sequence/hash.
Do not add complexity until the simulator requires it.

## 5. P1 — Physical architecture validation
Do not buy or build a custom vending machine yet.
First produce: workflow simulation, hardware BOM, component cost model, enclosure concept, payment architecture, inventory mechanism, controller architecture, security model, and failure-state matrix.
Then select commercially available components for the prototype.

## 6. P1 — Pennsylvania legal workstream
The existing docs/LEGAL-PA.md is a research baseline, not launch authorization.
Next research: PA MMO partner map; exact smart-dispenser architecture; employee involvement; facility requirements; verification; seed-to-sale integration; and any required DOH approval.
For each product category map: product → classification → permitted channel → venue → machine role → customer verification → approval → evidence.
Do not infer commercial legality from supplier shipping policies.

## 7. P1 — Crowdfunding readiness gate
Before publishing the final campaign: documented prototype architecture; realistic BOM; calculated funding target; accurate legal pathway; reviewed rewards; campaign/business structure review; insurance research; venue strategy; public risk register; spending ledger; measurable milestones.

## 8. P2 — Public trust layer
Create a public dashboard containing project stage, money raised, money spent, blockers, completed milestones, next milestone, major risks, legal research status, prototype status, uptime, and pilot metrics when available.
Show failures as well as successes.

## 9. Architecture equation
Adaptive Value = Legal Feasibility × Customer Demand × Machine Reliability × Unit Economics × Operational Scalability × Trust
Because this is multiplicative, a near-zero factor can dominate the entire system.

## 11. Definition of MVP
The MVP is not the vending machine.
The MVP is a reproducible system that can prove one legal/controlled retail workflow, measure it, audit it, and calculate whether the economics justify physical deployment.

## 12. Founder rule
For every recurring task: DO → DOCUMENT → STRUCTURE → AUTOMATE → DELEGATE.
The founder's highest-value asset is the system created from the work.
